# 05 アーキテクチャ / 技術構成

## 方針

- **Webアプリ先行**（決定済み）。低コスト・反復容易を優先。
- 現デモ（単一HTML・localStorage・ダミー相場）から、**段階的に**サーバ/DB・認証・相場バッチを足す。一気に作り直さない。

## 現状

```
[ブラウザ] 単一 index.html (HTML+CSS+JS)
   └ localStorage に items を保存
   └ 相場はクライアントで擬似生成（MARKET 配列 + genHistory）
```

## 目標構成（フェーズ1：MVP）

```
[ブラウザ SPA] ── HTTPS ──> [APIサーバ] ──> [DB]
   認証(JWT/セッション)            │            users / collection_items / works
   画像アップロード ───────────────┼──> [オブジェクトストレージ] (画像)
                                   └──> price_points は当面 manual のみ
```

### 技術選定（たたき台・要確定）

| レイヤー | 候補 | 備考 |
|---|---|---|
| フロント | 現バニラJSを段階移行 → SPAフレームワーク（React/Svelte/Vue いずれか） | デモのUIは流用可。まずはバニラのままサーバ接続でも可 |
| 認証 | OAuth(Google) ＋ メールリンク or 既製Auth（Auth系SaaS） | 自前パスワード管理は最小化 |
| API | 軽量フレームワーク（Node/TS, Python など使い慣れた言語） | チーム/本人のスキルで決定 |
| DB | PostgreSQL（リレーショナル。works名寄せ・集計に向く） | 無料枠のあるマネージドを推奨 |
| ストレージ | オブジェクトストレージ（画像） | dataURL埋込を脱却 |
| ホスティング | PaaS/サーバレス（低コスト枠） | 個人運用前提でコスト最小 |

> 言語・FWは本人/チームの習熟度で決めてよい。**重要なのは「DB・認証・画像ストレージ・相場バッチ」の4分離**であって、特定スタックではない。

## 目標構成（フェーズ2：相場実データ化）

```
            [収集ジョブ/バッチ] ──(04の決定したソース)──> price_points
                  │ 定期実行（cron/ワーカー）
                  └ 正規化・名寄せ → works に紐付け
[APIサーバ] ──> 集計(中央値/最高/トレンド) ──> 相場表示・自動相場反映(market_source=auto)
```

- 相場収集は**APIサーバと分離した非同期ジョブ**にする（NFR-8）。落ちても本体が止まらない。
- 集計はバッチで事前計算 or マテビュー化（NFR-1の性能）。

## 移行ステップ（破壊的にしない）

1. デモのデータ構造を維持したまま、保存先を localStorage → API/DB に差し替え。
2. 認証を追加し、items に user_id を付与。
3. 画像を dataURL → アップロード/URL参照へ。
4. （04決定後）相場を manual → auto ソースへ。

## 非機能との対応

- NFR-1 性能：一覧/検索はDBインデックス＋ページング。1,000点で1秒以内。
- NFR-3 セキュリティ：TLS、トークン、画像のアクセス制御。
- NFR-5 保全：DB自動バックアップ＋ユーザーエクスポート常設。
- NFR-9 コスト：マネージド無料枠中心、相場バッチは頻度を絞る。
