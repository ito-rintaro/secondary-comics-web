# 04 相場データ取得方針 ★要意思決定（未決定）

本プロダクト最大の分岐点。**技術コスト・法務リスク・データ品質**が三すくみ。
ここが決まらないと `03`（price_points運用）・`05`（バッチ基盤）・`07`（収益）・`08`（リスク）が固まらない。

## 評価軸

- **品質**：実勢価格に近いか、コンディション別に取れるか、鮮度。
- **法務**：各サービスの利用規約(ToS)・著作権・不正競争・スクレイピングの適法性。
- **コスト/工数**：収集基盤・メンテ。
- **継続性**：先方の仕様変更・BANで止まらないか。

## 案A：メルカリ等のsold価格を収集（hobipedia型）

- **品質**：◎ 実勢価格そのもの。状態別も取りやすい。
- **法務**：△〜× 各社ToSでスクレイピング/自動取得を禁止している場合が多い。画像・説明文の転載は著作権/不競法リスク。**要法務確認**。
- **コスト**：高（収集基盤・BAN対策・正規化・名寄せ）。
- **継続性**：低〜中（仕様変更・遮断リスク）。
- メモ：hobipediaは「価格(数値・統計)のみを情報提供、画像/本文は転載しない」形で運用していると推測。**数値の事実＋出所明示＋キャッシュ最小化**ならリスクを下げられるが、ToS順守の可否は個別判断が必要。

## 案B：公式API / 提携データ（合法ソース中心）

- 候補：楽天Books API（新刊・定価・書誌）、各種書誌API（openBD等でISBN/書影）、アフィリエイトAPI、buy取店との提携データ、（あれば）オークション公式データ。
- **品質**：△ 「定価・書誌」は取れるが**中古プレミア実勢は弱い**。提携で補完が必要。
- **法務**：◎ 規約内で合法。
- **コスト**：中（API実装）。
- **継続性**：高。
- メモ：書誌・書影・新刊検出はAPIで、プレミア相場は案C/Dで補完するハイブリッドが現実的。

## 案C：ユーザー手入力＋自己申告相場（MVPデフォルト）

- **品質**：× ユーザー依存・主観的。だが「自分のコレクションの管理」用途では当面成立。
- **法務**：◎ リスクほぼ無し。
- **コスト**：低。
- **継続性**：高。
- メモ：デモが既にこれ。MVPはこれで出し、`market_source=manual`。後で自動ソースへ差し替え可能な設計に。

## 案D：クラウドソース集計（ユーザーの取引/相場報告を匿名集計）

- ユーザーが「いくらで買った/売れた」を任意登録 → 母数が増えれば独自相場に。
- **品質**：初期×→母数次第で○（独自データ資産になる）。
- **法務**：◎（自社内データ）。
- **コスト**：中（インセンティブ設計が必要）。
- **継続性**：高。
- メモ：マイカ/スニダンも自プラットフォームの取引が相場の源泉。長期的に最も筋が良い。

## 推奨（たたき台）

**段階的ハイブリッド**：

1. **MVP**：案C（手入力）でリリース。同時に案Bの**合法API（書誌・書影・新刊検出）**を組み込み、登録UXを楽にする。
2. **フェーズ2**：案Dを開始（取引/相場の自己申告を蓄積）。
3. **案Aは法務確認が取れた範囲でのみ限定採用**（例：数値統計のみ・出所明示・キャッシュ最小・robots/ToS順守）。可否が不明なうちは実装しない。
